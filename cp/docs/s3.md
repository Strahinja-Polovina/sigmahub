# Object storage (P2-1 MinIO, P2-2 SeaweedFS)

SigmaHub provisions S3-compatible object storage as a first-class resource
(kind `s3`), rendered exactly like a database: a pinned engine image, a data
volume, and a container that publishes the S3 API **only** on the server's
WireGuard mesh address — never a public interface. The CP generates the root
credentials, wraps them under the per-org DEK, and reveals them (audited) to
Project Admins. The agent has zero S3-specific code: both engines take their
root credentials purely through environment variables.

## Engines

Two engines live behind the one `s3` kind. The engine is chosen at create time
via the resource spec (`{"engine": "..."}`) and defaults to MinIO; the concrete
engine is recorded on the credentials row and drives every downstream render.

| Engine      | Image (pinned)                          | S3 port | License     |
| ----------- | --------------------------------------- | ------- | ----------- |
| `minio`     | `minio/minio:RELEASE.2025-04-22…`       | 9000    | AGPL-3.0    |
| `seaweedfs` | `chrislusf/seaweedfs:3.94@sha256:d8ab…` | 8333    | Apache-2.0  |

SeaweedFS exists as the **license hedge**: MinIO is AGPL-3.0, and pinning a
second, Apache-2.0 engine behind the same abstraction means the AGPL risk can
never become a blocker. Both engines are pinned — MinIO by immutable release
tag, SeaweedFS by digest.

### Why SeaweedFS is digest-pinned

SeaweedFS reads its admin S3 identity from `AWS_ACCESS_KEY_ID` /
`AWS_SECRET_ACCESS_KEY` when no config file is present. That env-var path is the
only one that stays engine-agnostic for the agent: the alternative
(`-s3.config` file) reloads only on SIGHUP, which would require engine-specific
agent code to signal. Upstream regressed the env-var path in 3.97
([#7311](https://github.com/seaweedfs/seaweedfs/issues/7311)); 3.94 works, so we
pin **3.94 by digest** to freeze that behavior. MinIO takes the same shape via
`MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`.

Only the S3 port is published on the mesh. SeaweedFS's `weed server -s3` also
starts master/volume/filer, but those ports stay container-internal.

## Allowlist

`CP_S3_ENGINES` gates which engines new resources may select, exactly like
`CP_DB_ENGINES` gates database engines. A typo fails boot rather than silently
disabling an engine.

- Default: `CP_S3_ENGINES=minio,seaweedfs` (both enabled).
- MinIO-only build: `CP_S3_ENGINES=minio`.
- Creating a resource whose engine is not in the allowlist fails loudly.

## Honest support matrix

Both engines speak the S3 API, so buckets and objects are managed identically
with any S3 client using the revealed root credentials. What does **not** map
1:1:

| Capability                    | MinIO           | SeaweedFS   |
| ----------------------------- | --------------- | ----------- |
| S3 API over the mesh          | yes             | yes         |
| Root credentials (env)        | yes             | yes         |
| Buckets via any S3 client     | yes             | yes         |
| In-dashboard bucket/key CRUD  | follow-up       | follow-up   |
| Built-in web console          | off (disabled)  | n/a         |
| License                       | AGPL-3.0        | Apache-2.0  |

In-dashboard bucket/key/quota CRUD is a follow-up (SIGMA-65) for **both**
engines — it needs a typed agent op mapping onto each engine's admin API
(MinIO's `mc` admin vs SeaweedFS's `s3.configure`). Until then the root
credentials manage everything, and the dashboard surfaces the same matrix on
the resource's storage panel so the trade-off is never hidden.

## Using it

```
aws s3 mb s3://my-bucket --endpoint-url http://<mesh-ip>:<port>
```

The endpoint, access key, and (audited) secret-key reveal are on the resource's
**Object storage** panel. The endpoint is reachable only from machines on the
org's mesh.
